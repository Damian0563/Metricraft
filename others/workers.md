# Supabase Workers Table

Metricraft stores uptime-monitoring configuration in the Supabase `public.workers` table referenced by `DATABASE_USERS`. Each row belongs to one app namespace and holds the full list of configured workers for that app.

## Schema

```sql
create table public.workers (
  id bigint generated by default as identity not null,
  created_at timestamp with time zone not null default now(),
  app_name text null,
  workers json null default '[]'::json,
  constraint workers_pkey primary key (id)
) TABLESPACE pg_default;
```

## Columns

| Column | Type | Description |
|--------|------|-------------|
| `id` | `bigint` | Surrogate primary key, generated by default as identity. |
| `created_at` | `timestamp with time zone` | Creation timestamp, defaulting to `now()`. |
| `app_name` | `text` | Application or project name. One workers row is created per app during sign-up. |
| `workers` | `json` | JSON array of configured workers for the app. Defaults to an empty array (`[]`). |

## `workers` column format

The `workers` column stores a JSON array. Each element is a JSON object with this shape:

```json
{
  "url": "https://example.com/health",
  "pollInterval": 10,
  "headers": {
    "Authorization": "Bearer token"
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `url` | `string` | Health-check or upstream endpoint the worker polls. Used as the unique key within an app. |
| `pollInterval` | `number` | Poll frequency in minutes. The dashboard accepts values from 5 to 60. |
| `headers` | `object` | Optional request headers sent on each poll. Omitted when empty. |

The backend reads and writes this column through `backend/db/workers.go`. At most **5 workers** are allowed per `app_name`.

## Relationship to other tables

- **`public.users`**: Linked by `app_name`. When a new user signs up, `CreateUser` inserts a matching row into `workers` with the same `app_name` and an empty `workers` array.
- **`worker_logs`** (in `DATABASE_LOGS`): Separate from this table. The worker process polls endpoints defined here and writes uptime results into `worker_logs`; deleting a worker removes its config from this table but does not automatically purge historical log rows.

## Backend usage

| Operation | Function | HTTP route |
|-----------|----------|------------|
| List | `GetWorkers` | `GET /dashboard/worker/list` |
| Create | `SaveWorker` | `POST /dashboard/worker/new` |
| Update | `UpdateWorker` | `PATCH /dashboard/worker/update` |
| Delete | `DeleteWorker` | `DELETE /dashboard/worker/delete/{url}` |

After a create, update, or delete, the backend also notifies the worker service over gRPC so in-memory polling is started, restarted, or cancelled. The worker process loads configuration from this table via `GetWorkers(appName)` using the `APPNAME` environment variable.
